Chromium Web 安全体系：同源策略、Cookie、CORS、XSS 与 CSRF

以同源策略为根，系统梳理 Chromium 承载的 Web 安全体系：Cookie 的属性与隔离、CORS 的跨源协商、XSS 的防线（CSP/Trusted Types）与 CSRF 的缓解（SameSite/Token），以及帧嵌入、Referrer、混合内容等配套机制。

Web 是一个攻击面极其特殊的环境：任何页面都可以加载并执行来自任意第三方的代码，用户同时登录着几十个站点。Chromium 的"业务安全"（相对于上一层的沙箱/多进程这类平台安全）就是在这个前提下建立的：用一组由浏览器强制执行的安全策略，把不可信代码圈死在它的来源之内。这些机制的共同根源只有一个——同源策略。

1. 同源策略：一切的根

同源策略（Same-Origin Policy, SOP）规定：一个源（origin = scheme + host + port）的文档或脚本，不能读取另一个源的资源内容。注意边界划分：

  • 被隔离的是"读"：跨源写（表单提交、img 加载、script 加载）默认是允许的，这是 Web 开放性的基础；跨源读取响应内容被禁止。
  • 隔离单位是源而非站点：https://a.com 与 http://a.com（scheme 不同）、a.com 与 b.a.com（host 不同）都互为跨源。子域之间需要显式 document.domain（已废弃，转向 COOP/COEP 体系）或 postMessage 协作。
  • CSSOM/DOM/存储/Cookie 全部受影响：跨源 iframe 的 DOM 不可读写、跨源的 localStorage/XHR 响应不可见、HttpOnly 的 Cookie 跨源 JS 不可读。

同源策略与上一节的多进程架构呼应：Site Isolation 把不同源放进不同进程，是把 SOP 的逻辑边界落到物理边界上——侧信道时代，逻辑隔离不够。

2. Cookie：凭据的载体

Cookie 是 Web 会话的默认凭据机制，也是绝大多数攻击（CSRF、会话固定、劫持）的目标。浏览器对 Cookie 的控制靠一组属性：

属性作用防的攻击
Secure仅 HTTPS 连接发送明文网络劫持
HttpOnlyJS（document.cookie）不可读XSS 窃取会话
SameSite限制跨站请求携带（Lax/Strict/None）CSRF、跨站泄露
Domain 作用域默认 host-only，显式 Domain 允许子域共享越权写入（配合前缀）
Path路径作用域（安全上很弱，仅约定）—
__Host- / __Secure- 前缀浏览器强制：__Host- 必须 Secure、无 Domain、Path=/子域攻击篡改父域 Cookie
Partitioned（CHIPS）按顶级站点分区存储，第三方 Cookie 每站一份跨站跟踪、站间凭据串联

SameSite 是近年最重要的变化：Lax（Chrome 默认）允许顶级导航 GET 携带 Cookie、禁止跨站 POST/iframe/XHR/fetch 携带；Strict 连顶级导航也不带；None 必须搭配 Secure。这直接把"跨站请求默默带凭据"这一 CSRF 的前提削掉了一大半——但 Lax 下的顶级 GET 导航仍然携带，CSRF 并未根除（见第 5 节）。

另外要区分 第一方与第三方 Cookie：iframe 中设置的 Cookie 属于第三方上下文。Chrome 正在以 CHIPS（Partitioned）+ 用户设置替代单纯的"第三方 Cookie 封杀"，方向是"分区的第三方 Cookie"——存在但彼此隔离，无法用于跨站串联身份。

3. CORS：跨源的受控放行

CORS（Cross-Origin Resource Sharing）不是防火墙，而是在同源策略上开的一扇受控的窗。它是服务器授权协议：服务器通过响应头声明"我允许哪个源以什么方式读我"。

3.1 简单请求与预检

  • 简单请求（GET/POST/HEAD + 安全的 Content-Type 等）：直接发出，响应带 Access-Control-Allow-Origin 时浏览器才把结果交给脚本。
  • 预检请求（preflight）：携带自定义头、PUT/DELETE 等方法的请求，浏览器先发一个 OPTIONS，带上 Origin、Access-Control-Request-Method / -Headers；服务器应答允许后，真实请求才发出。

预检的设计意图很微妙：保护的是"旧服务器"。Web 上存在大量不支持 CORS 的老服务，若无预检，浏览器发出的新式跨源写请求会真实打到它们身上。预检先确认服务器"懂 CORS"，不懂就拦截在真实请求之前。

3.2 凭据与通配符

  • fetch(url, {credentials: 'include'}) 跨源携带 Cookie 时，服务器必须回 Access-Control-Allow-Origin: https://具体源（不能是 *）且 Access-Control-Allow-Credentials: true。
  • 常见漏洞模式：服务器把请求头里的 Origin 原样反射回 Allow-Origin，等于向任意站点开放了带凭据的读取权限。白名单校验是唯一正解。
  • CORS 只管"读"；阻止跨源写请求靠不了 CORS——那是 CSRF token 与 SameSite 的职责。

4. XSS：注入类攻击与防线

XSS（Cross-Site Scripting）是攻击者把脚本注入受害页面执行：存储型（注入进数据库）、反射型（注入进 URL 回显）、DOM 型（前端拼接未转义数据）。XSS 一旦成立，同源策略就反向为攻击者服务——脚本获得受害源的全部权限：读 Cookie（无 HttpOnly 时）、发任意同源请求、篡改 DOM、记录键盘。

防线分三层：

  1. 输出编码（应用层，治本）：按上下文转义（HTML 实体、JS 字符串、URL、CSS），框架默认转义（React/Vue 的 JSX 与模板）。这是唯一完整解。
  2. CSP（Content-Security-Policy，浏览器强制）：
    • default-src 'self' + 显式脚本源，内联脚本（<script> 直接量、内联事件处理器）默认被禁；
    • nonce 或 hash 模式（script-src 'nonce-xxx'）兼顾内联需求与白名单；
    • 限制面不止脚本：connect-src、frame-ancestors、base-uri 等覆盖注入点。
    • Content-Security-Policy-Report-Only 用于灰度观察。
  3. Trusted Types（Chromium 原生支持）：把 sink（innerHTML、eval 等）锁死，只接受经过显式策略创建的 TrustedScript/TrustedHTML 对象，把"字符串进 DOM"变成类型错误。配合 CSP require-trusted-types-for 'script'，DOM 型 XSS 在大规模前端代码库里可被架构性消除。
  4. 辅助：HttpOnly 让偷 Cookie 不成（但不防"以受害者身份发请求"）；Sanitizer API 正在标准化安全清洗 HTML 的原语。

关键认知：CSP 与 Trusted Types 是纵深防御而非替代品——编码漏了，策略挡住；策略配置过宽（如允许 unsafe-inline 或存在可被绕过的 JSONP 端点），编码兜底。CSP 的绕过史本身就是一个安全研究方向（script gadgets、严格 CSP 的现实可行性）。

5. CSRF：冒名请求与缓解

CSRF（Cross-Site Request Forgery，常被误写为 CSFR）利用的不是漏洞代码，而是 Web 的默认行为：跨站请求会自动带上目标站点的 Cookie。恶意页面上一个 <form action="https://bank.com/transfer" method="POST"> 自动提交，浏览器就会带着你在 bank.com 的登录态发出转账请求——服务器看到的是"已认证的合法用户"。

缓解体系：

  • SameSite Cookie（浏览器侧）：Chrome 默认 Lax 已拦截绝大多数跨站 POST 场景。但顶级导航的跨站 GET 仍携带 Cookie，且旧浏览器/某些内嵌 WebView 不完全遵守——不能单独依赖。
  • CSRF Token（应用侧，经典主防线）：表单内嵌服务端签发的随机 token，服务器校验。攻击者跨站无法读取 token（同源策略），伪造的请求必然缺 token。双提交 Cookie（cookie + 请求字段各带一份）是无状态部署变体，但要小心子域可写 Cookie 的场景（配合 __Host- 前缀）。
  • Origin/Referer 校验（服务侧）：校验请求头来源是否本站。可行但 Referer 可能缺失/被策略裁剪，Origin 头在部分老客户端缺失。
  • Fetch Metadata（浏览器侧，新世代的解）：Sec-Fetch-Site: cross-site、Sec-Fetch-Mode 等由浏览器自动附加、JS 不可伪造。服务器（或边缘）据此直接拒绝跨站请求——把 CSRF 防御从"每站自建 token"变成"平台级请求来源标签"。Resource Isolation Policy（RIP）模式就是基于它。

注意 CSRF 与 CORS 的分工：CORS 阻止读跨源响应；CSRF 防的是写（冒名请求本来就"能发"，只是不能被脚本读到响应）。所以 CSRF 的防御核心是"让服务器拒绝不可信来源的写"，而不是阻止请求发出。

6. 配套机制：一张更完整的地图

机制解决什么
X-Frame-Options / CSP frame-ancestors点击劫持（Clickjacking）：禁止被恶意站嵌入 iframe 遮罩诱骗点击
Referrer-Policy控制跨站导航携带的来源信息，防 URL 内敏感参数泄露（strict-origin-when-cross-origin 为 Chrome 默认）
HSTS + 混合内容拦截强制 HTTPS、阻止 HTTPS 页面加载 HTTP 子资源（混合内容分可阻断/可选阻断两类）
COOP/COEP/CORP跨源 opener/嵌入隔离：window.opener 关系切断、跨源子资源必须授权（为 Spectre 时代的 XS-Leak 提供进程级隔离前提）
Permissions-Policy按来源/iframe 控制摄像头、地理定位等高权限 API 可用性
postMessage origin 校验跨源通信的受控通道；不校验 e.origin 是常见注入点
iframe sandbox 属性对嵌入内容降权：禁脚本/表单/同源访问等，粒度化委托
XS-Leak 防护族防侧信道读跨源响应元信息（长度、时间、缓存状态）：COEP、Partitioned 缓存、Fetch Metadata

可以把这些机制按"信任边界的维护者"归类：浏览器强制（SOP、SameSite、CSP、混合内容、Fetch Metadata、COOP/COEP）与服务器声明 + 浏览器执行（CORS、frame-ancestors、Referrer-Policy）。业务方真正要写代码防的，只剩输出编码与 CSRF token 这类应用层逻辑；其余都在向"平台兜底"收敛——这也是 Web 安全十余年演进的主线：把安全正确性从每个开发者的自觉，变成浏览器的默认。

7. 小结与心智模型

  1. 同源策略是公理：默认隔离，CORS 是受控放行，Site Isolation 是物理加固。
  2. 凭据链看 Cookie：Secure/HttpOnly/SameSite/前缀/Partitioned 各守一段，会话安全=属性配置+作用域最小化。
  3. 读与写分治：CORS 管读，CSRF 管"写"，XSS 管"注入后什么都做"。三者常被混为一谈，但防线完全不同。
  4. 纵深防御：应用层编码/Token 为主，浏览器策略（CSP、Trusted Types、SameSite、Fetch Metadata）为盾，二者互为兜底。

延伸方向：XS-Leak 攻击面系统整理、严格 CSP 在大型工程的落地案例（Google 的经验）、Trusted Types 迁移方法论、以及 Cookie 的演进（CHIPS 与 Storage Access API 的博弈）。
