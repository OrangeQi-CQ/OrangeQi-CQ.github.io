跨境 UDP 定向丢包排障实录：从 WireGuard 握手失败到国内节点中继

电脑和手机同时连不上，服务器配置看起来全对。真正的问题不在任何一台机器的配置文件里，而在两段网络之间。

更新 2026-11-03记录 2026-11-03

这是一次「原本能用、突然全断」的排查记录。海外节点上的 WireGuard 服务端一切正常、密钥匹配、端口在听、防火墙放行，客户端配置也没改过，但电脑和手机就是连不上：客户端显示「已发送几百字节、收到 0 字节」，服务端看不到新的握手。

最后定位到的原因很反直觉：跨境链路上，WireGuard 默认端口 51820 作为「源端口」的 UDP 包被定向丢弃了。换个监听端口就活了。为了让它稳定可用，又加了一台国内节点做 UDP 中继，形成「国内中转 → 海外出口」的两跳结构。

下面把方法、工具、命令和踩过的坑都整理出来。文中地址、密钥一律使用文档示例值，实际配置保存在本机。

现象：三个「看起来都对」

故障刚出现时，有三处信息同时指向「配置没问题」，很容易误判：

  1. 客户端显示隧道已建立。WireGuard 界面是绿色的，wg show 能看到接口和 peer，只有 transfer 是 0 B received。
  2. 服务端配置齐全。wg show 显示监听端口、两个 peer、AllowedIPs 都对；ip_forward=1，MASQUERADE 规则也在。
  3. 服务器完全可达。ping 通（60 ms 左右）、SSH 通、甚至历史上一天前还有成功的握手记录和上 GB 的流量计数。

真正有用的信号只有一个：sent 在涨、received 恒为 0，服务端没有新的握手时间。这说明客户端在发、服务端没收到或回了但客户端收不到。接下来所有的动作，都是为了把「哪一段断了」变成可观测的事实。

先把问题切成四段

链路一长，最忌讳「在一台机器上空转」。把整条路径拆成四段，每一段都要拿到独立证据：

[客户端] --A--> [国内链路] --B--> [中转节点] --C--> [海外节点] --D--> 回程
段要回答的问题证据来源
A客户端到底有没有把包发出去？发给了谁？客户端 wg show 的 transfer、endpoint
B包有没有到达中转/海外节点的网卡？对端 tcpdump -i eth0 'udp and port 51820'
C对端有没有回包？回给了哪个地址端口？同一份抓包的 Out 方向、wg show 的 latest handshake
D回包有没有回到客户端？客户端 netstat -s -p UDP 的收包计数、本机抓包

关键点：「对端抓到了」不等于「客户端收得到」。两端必须同时抓、按时间戳对，才能判断丢在哪一侧。

手法一：不用管理员权限的 WireGuard 握手探针

最难受的局面是：想验证「服务端会不会回我的包」，但装隧道要管理员权限、要建虚拟网卡、还可能把整机网络搞断。这时可以只做一件事——用脚本发一个合法的握手初始化包，看对方回不回。

WireGuard 的握手消息是固定 148 字节的 Noise_IKpsk2 初始化包。只要能拿到客户端静态私钥和服务端公钥，就可以用 Python 手搓一个，从普通 UDP socket 发出去，不需要 root、不创建网卡、不影响系统路由：

04 00 00 00  sender_index(4)
ephemeral(32)              ← 临时公钥
encrypted_static(48)       ← 32 字节静态公钥 + 16 字节 tag
encrypted_timestamp(28)    ← 12 字节 TAI64N + 16 字节 tag
mac1(16)  mac2(16)
──────────────────────────
合计 148 字节

判定标准非常明确：

  • 收到 92 字节、type=2 的报文 → 服务端接受了你的密钥并回了握手响应，路由、密钥、peer 全部正确。
  • 收到 type=3 → 服务端在负载下要求 cookie，链路也是双向通的。
  • 什么都没有 → 要么包没到，要么对方没回，要么回程断了（配合两端抓包区分）。

这个探针把「客户端软件、路由表、DNS、虚拟网卡」这些变量全部排除掉，只测最纯粹的「UDP 双向可达 + 密钥被接受」，是本次定位里性价比最高的一步。

握手实现的两个坑

自己实现时踩了两个坑，都不是「大概对」就能过的，密码学部分必须逐字节一致：

  1. 初始 hash 里要混入 IDENTIFIER。不是简单的 HASH(CONSTRUCTION)，而是 InitialChainKey = HASH("Noise_IKpsk2_25519_ChaChaPoly_BLAKE2s")， InitialHash = HASH(InitialChainKey ‖ "WireGuard v1 zx2c4 Jason@zx2c4.com")， 之后才是 HASH(InitialHash ‖ 对端静态公钥)。少这一步，包结构看着完全正常，对方静默丢弃。
  2. MAC1 是「带密钥的 BLAKE2s-128」，不是 HMAC。即 BLAKE2s(key = HASH("mac1----" ‖ 对端公钥), data = 前 116 字节, digest_size = 16)。 用 HMAC 算出来是 32 字节，报文长度会变成 164 字节，一眼就能看出来不对。

调试技巧：先验证 MAC1 能不能对上——让服务端主动发起握手（把临时 peer 的 endpoint 指向本地监听端口，然后从服务端 ping 对端隧道地址触发），抓下它发出的真实 148 字节包，用自己实现的 MAC 函数去复算，能对上就说明哈希与 MAC 实现正确，剩下的问题只可能在 AEAD/KDF 链上。

手法二：用 UDP 栈计数器判断「包到没到本机」

「我没收到」可能是应用层没收到，也可能是包根本没到。Windows 上最省事的判据是 netstat -s -p UDP 的两个数字：

netstat -s -p UDP | findstr /C:"Datagrams Received" /C:"No Ports" /C:"Receive Errors"

# 采样 → 发一个探针 → 再采样
观察结果结论
Datagrams Received 不增长包没有进本机协议栈 → 丢在网卡之前（运营商、云安全组、路由器）
增长，但应用没收到，No Ports 也涨包到了，但目的端口没有 socket 接收 → NAT 映射问题或端口对不上
正常增长且应用收到这一段链路没问题，往上游查

一定要用「同一个网络里其他服务的 UDP 回包」做对照实验（公共 DNS、STUN、NTP 都行）。如果别人的 UDP 回包能收到、只有目标 IP 收不到，问题就被锁定到「特定对端」，而不是「本机防火墙」。

手法三：STUN 查 UDP 出口地址

有一种容易被忽略的故障：服务器 TCP 出口是 A 地址，UDP 出口却是 B 地址（NAT 非对称）。这时客户端会看到「回包来自一个我没发过的地址」，直接被丢掉。

用任何一个 STUN 服务器就能验证——回包里带 XOR-MAPPED-ADDRESS，就是对方看到的你的 UDP 源地址：

import os, socket, struct

pkt = struct.pack(">HHI", 1, 0, 0x2112A442) + os.urandom(12)   # Binding Request
s = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
s.settimeout(3)
s.sendto(pkt, ("stun.example.net", 3478))
data, addr = s.recvfrom(2048)      # 解析 XOR-MAPPED-ADDRESS 即可

本次实测：服务器 UDP 反射地址与 curl ifconfig.me 得到的 TCP 出口地址完全一致，排除了 NAT 非对称这条支线。

手法四：两端同时抓包 + conntrack 看回程

确认了「发得出去、对端收得到、对端也回了」之后，剩下的唯一问题就是回程。这时两端的抓包必须同时开，并且要能看出方向：

# 服务端：只抓 51820，看 In / Out 两个方向
sudo tcpdump -n -i eth0 -c 20 'udp and port 51820'

# 中转节点：同时看两侧（客户端方向 + 海外方向）
sudo tcpdump -n -i eth0 -c 30 'udp and (host <客户端公网IP> or host <海外节点IP>)'

再配上 conntrack -L，状态字段会直接告诉你答案：

udp 17 23 src=客户端 dst=中转 sport=9685 dport=51820
       [UNREPLIED]                     ← 关键：只出去，没回来
       src=海外 dst=中转 sport=51821 dport=40064

[UNREPLIED] 加上「海外节点抓包里明明有 Out 方向的 92 字节响应」，就说明回包在到达中转节点网卡之前就被丢了，不是 iptables 的问题——这一步能省掉大量在规则上空转的时间。

定位：跨境链路对「源端口 51820」的定向丢包

真正把原因钉死的是一组对照实验：让海外节点用不同源端口向中转节点的同一个端口发 UDP，观察哪些能到达。

源端口目的端口是否到达
38093 / 54345 / 60032（随机高位）40003 / 40025 / 40095✅ 到达
5182140025✅ 到达
4000140025✅ 到达
44340025✅ 到达
5182040025❌ 一个都没到

同一对 IP、同一段时间、同一个目的端口，只换源端口——只有 51820 被丢。结论很明确：这条跨境链路上有规则专门针对 WireGuard 默认端口的 UDP，与客户端、密钥、系统配置都无关。这也解释了为什么在转发节点上怎么改 iptables 都不生效——包根本没到网卡。

顺带一个方法论：WireGuard 的回包源端口永远等于服务端监听端口。所以只要换掉服务端监听端口，回包源端口就一起变了；客户端侧不需要任何改动（客户端连的仍是中转节点的 51820）。

中继方案：国内节点做纯 UDP 转发

端口换掉后，海外节点的回包能穿过跨境链路了，但客户端仍然不能直连海外节点（客户端所在的运营商网络对该地址的 UDP 同样不可靠）。所以加一台国内节点做中转，客户端连国内（国内段 UDP 通畅），国内节点再转发到海外。

这里是内核态转发，不是 userspace 代理，性能损耗极小：

# 1) 开启转发
sysctl -w net.ipv4.ip_forward=1

# 2) 目的地址转换：客户端打到本机 51820 的包，转给海外节点的 51821
iptables -t nat -A PREROUTING -p udp --dport 51820 \
  -j DNAT --to-destination <海外节点IP>:51821

# 3) 源地址转换：把源地址改成中转节点自己，这样回包会回到这里
#    注意把源端口收敛到固定区间，方便安全组按端口段放行
iptables -t nat -A POSTROUTING -p udp -d <海外节点IP> --dport 51821 \
  -j SNAT --to-source 10.0.0.15:40000-40099

# 4) FORWARD 默认策略常常是 DROP（装了 Docker 的机器尤其如此），必须显式放行
iptables -I FORWARD 1 -p udp -d <海外节点IP> --dport 51821 -j ACCEPT
iptables -I FORWARD 1 -m conntrack --ctstate RELATED,ESTABLISHED -j ACCEPT

为什么 SNAT 端口一定要收敛

这是本次最隐蔽的一个坑。云安全组是按端口匹配的：

  • 用 MASQUERADE 时，源端口由内核从临时端口里分配，每次会话都可能不同（9685、40064、40095…）。
  • 海外节点回包的目的端口就是这个临时端口，而安全组只放行了少数几个端口 → 回包在到达网卡之前就被丢弃，tcpdump 连影子都看不到。
  • 逐个端口加白是不可维护的。正确做法是把 SNAT 源端口收敛到一个固定区间（如 40000-40099），然后在安全组里按源 IP放行全部 UDP 端口，或放行这一小段端口。

判断依据就是 conntrack 里那条 [UNREPLIED]：它说明 POSTROUTING 已经把包发出去了（规则命中），但反向包从未回来。

持久化：重启后规则不能丢

iptables 规则默认不落盘。用 systemd 的 oneshot 服务在启动时重新应用，比依赖 iptables-persistent 更直观，也便于把「幂等删除再添加」写进脚本：

[Unit]
Description=WireGuard UDP relay (51820 -> overseas:51821)
After=network-online.target
Wants=network-online.target

[Service]
Type=oneshot
RemainAfterExit=yes
ExecStart=/usr/local/sbin/wg-relay.sh

[Install]
WantedBy=multi-user.target
systemctl daemon-reload
systemctl enable --now wg-relay.service
echo 'net.ipv4.ip_forward=1' > /etc/sysctl.d/99-wg-relay.conf

脚本要写成幂等的：先 -D 删除同名规则（不存在就 || true），再 -A 添加，避免重复执行堆出一串重复规则。

最终配置片段

客户端只需要把 Endpoint 指向中转节点，其余（密钥、隧道地址、MTU、keepalive）保持不变：

[Interface]
PrivateKey = <客户端私钥>
Address = 10.66.66.2/24
DNS = 1.1.1.1
MTU = 1380

[Peer]
PublicKey = <海外节点公钥>
Endpoint = 122.51.x.x:51820      ; 连中转节点，不是直连海外
AllowedIPs = 0.0.0.0/0
PersistentKeepalive = 25

海外节点的 /etc/wireguard/wg0.conf 只改监听端口，其他不动：

[Interface]
Address = 10.66.66.1/24
ListenPort = 51821              ; 原 51820 在这条链路上会被针对性丢弃
PrivateKey = <服务端私钥>
PostUp = iptables -A FORWARD -i wg0 -j ACCEPT; iptables -A FORWARD -o wg0 -j ACCEPT; iptables -t nat -A POSTROUTING -o eth0 -j MASQUERADE
PostDown = iptables -D FORWARD -i wg0 -j ACCEPT; iptables -D FORWARD -o wg0 -j ACCEPT; iptables -t nat -D POSTROUTING -o eth0 -j MASQUERADE

[Peer]
PublicKey = <客户端公钥>
AllowedIPs = 10.66.66.2/32

[Peer]
PublicKey = <手机公钥>
AllowedIPs = 10.66.66.3/32

安全组需要三条（云控制台）：客户端到中转的 UDP/51820；中转访问海外的 UDP/51821；以及中转侧按源 IP 放行来自海外节点的 UDP（源 <海外节点IP>/32，端口全部或 40000-40099）。

踩坑清单

这次排查里，一半时间花在了下面这些坑上。按「症状 → 原因 → 处理」记录，供下次直接查表。

症状原因处理
wg setconf 报 AllowedIP is not in the correct format: 10.66.66.2/32[Peer]配置文件少了一个换行，两个 [Peer] 段粘在一起。启动时没报错是因为文件在接口启动之后才被改坏，跑了几天一直没重启补换行，并用临时接口验证：ip link add wgtest type wireguard; wg-quick strip wg0 | wg setconf wgtest /dev/stdin。这类错误平时完全无感，重启即断
WireGuard 界面显示已连接，但整条链路从没通过隧道服务其实没在运行（服务被卸载或崩溃），只看 GUI 会误判交叉验证四件事：Get-Service WireGuardTunnel*、ipconfig 里有没有虚拟网卡、路由表有没有隧道网段、wg show 有没有接口
客户端 0 B received，服务端也没握手客户端发出的握手包到不了服务端，或者回包回不来两端同时抓包 + conntrack 看 [UNREPLIED]；再用不同源端口/不同主机做对照，区分「IP 被拦」还是「端口被拦」
中转上 tcpdump 完全看不到回包云安全组按端口匹配，SNAT 后的目的端口不在放行范围，包在网卡之前就被丢把 SNAT 端口收敛成固定区间，或按源 IP 放行 UDP 全部端口
改了 iptables 规则仍然不通真正生效的规则在 nft 里（云厂商安全组件常写 *-FIREWALL-INPUT），iptables -S 看不到nft list ruleset 完整看一遍；同时确认 FORWARD 策略可能是 DROP（装过 Docker 的机器默认如此）
ssh -i key 报 Bad permissions ... This private key will be ignoredWindows 上私钥文件对 Everyone 可读，OpenSSH 拒绝使用icacls key /inheritance:r /grant:r "$env:USERNAME:(F)"；临时排查可复制到私有目录再收紧权限
远程执行脚本「莫名其妙没跑完」pkill -f udp_echo_server 把执行它的那条 ssh 命令行也匹配进去了，直接把自己的 shell 杀掉用不会自匹配的写法：pkill -f "udp_echo[_]server"
PowerShell 里给 ssh 传多行脚本，远端报各种语法错误双引号、$、> 在 PowerShell → ssh → 远端 shell 三层里被反复解释不要在命令行里拼脚本：把脚本写到本地文件，通过 cat file | ssh host "sudo bash -s" 送进去；密码认证的场景用 paramiko 之类的库直接开 channel
curl -4 ifconfig.me 结果看起来是 IPv6当前网络 IPv6 优先，不少站点直接返回 IPv6 地址显式用 curl -4 或查询 IPv4 专用接口；排查出口地址时别被地址族误导
全隧道一开，整机断网AllowedIPs = 0.0.0.0/0 把默认路由交给隧道，隧道半通时所有流量都进黑洞先准备好回滚命令（wireguard.exe /uninstalltunnelservice <名字>），并保留一个能直连的 SSH 通道
能 ping 通隧道地址，网页却打不开多一跳后路径 MTU 更小，大包被丢把客户端 MTU 从 1380 降到 1280 再试
手机端无法复用「SSH 隧道」方案iOS 没有能跑 SSH 代理的通用客户端移动端只能连真实的 TCP/UDP 端口，所以要解决的是服务端端口可达性，而不是在客户端做花样

验证清单

改完之后按顺序验收，每一步都要有明确预期，不要跳步：

  1. 握手：wg show 出现 latest handshake: 几秒前，且 received 不再是 0。
  2. 隧道内连通：ping 10.66.66.1 通（延迟含两跳，200–400 ms 属正常）。
  3. 出口正确：curl -4 ifconfig.me 返回海外节点地址。
  4. DNS：随便解析一个域名，确认走的是隧道内的解析器而不是本地 ISP。
  5. 大流量：下载一个大文件，确认 MTU 没问题（不卡在半路）。
  6. 重启验证：重启中转节点，确认 wg-relay.service 自动把规则装回去。

可复用的排查顺序

把这次的经验压缩成一条通用路径，遇到「隧道连不上」可以直接照着走：

  1. 先确认隧道真的在跑：虚拟网卡、服务、wg show、路由表，四者对照，别看界面颜色。
  2. 再确认服务端在听：ss -lunp，以及密钥是否匹配（客户端私钥推导出的公钥要等于服务端配置的 peer）。
  3. 拿到双向证据：两端同时 tcpdump，看 In 有没有、Out 有没有。
  4. Out 有、客户端收不到：查 conntrack 的 [UNREPLIED]，查云安全组的回程端口，查 NAT 源端口是否在放行范围。
  5. In 就没有：查安全组、主机防火墙、nft，再用「换源端口 / 换目的主机」做对照，判断是按 IP 拦还是按端口拦。
  6. 确认是链路问题后：换端口、换 IP、加中转，而不是继续在配置里找原因。

最后一点体会：WireGuard 的「握手成功」只证明两端能交换协议消息，不证明转发、NAT、DNS、MTU 都正确；反过来，「握手失败」也不一定是配置错了——本次从头到尾配置文件都是对的，错的是包在网络上走的路。
