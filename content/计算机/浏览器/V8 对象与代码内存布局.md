JavaScript 表面上是"一切皆对象"的动态语言，但 V8 为了达到接近静态语言的性能，在内存布局上做了大量工程优化。理解 V8 如何在堆上表示对象和代码，是理解 JS 性能模型的关键。

## 1. 核心设计思想

V8 不把 JS 对象当成"哈希表/字典"来存储。它的核心思路是：

> **把对象表示成紧凑的 struct，把"形状/类型"信息抽离出来共享，通过内联缓存让属性访问接近结构体字段访问的速度。**

这和 Python 的 dict 对象、Ruby 的 instance variable hash 完全不同——后者每个对象自带一个哈希表，而 V8 对象本身只是一块紧凑的内存，"它有哪些属性、叫什么名字"这些元信息放在单独的 **Map（隐藏类）** 里，由多个同形状对象共享。

## 2. JS 对象的内存布局

### 2.1 基本结构

一个 V8 对象（`JSObject`）在堆上大致长这样：

```
┌─────────────────────────┐  低地址
│   Map 指针 (4/8 bytes)   │ ────→ 指向隐藏类（描述对象形状）
├─────────────────────────┤
│  Properties 指针        │ ────→ 命名属性的后备存储（慢属性）
├─────────────────────────┤
│  Elements 指针          │ ────→ 数字索引元素的后备存储（数组）
├─────────────────────────┤
│  In-object Slot 1       │  ← 内联属性值（直接存在对象体内）
├─────────────────────────┤
│  In-object Slot 2       │
├─────────────────────────┤
│  ...                    │
└─────────────────────────┘  高地址
```

关键三点：

1. **Map 指针**：每个对象第一个槽位都指向它的"隐藏类"，描述这个对象的形状
2. **内联属性（in-object properties）**：常见的几个属性直接存在对象体内，按偏移量访问，速度最快
3. **Properties / Elements 分离**：命名属性和数字索引元素分开存储，优化数组访问

### 2.2 为什么这样设计

```js
const point = { x: 10, y: 20 };
```

V8 不会给 `point` 建一个 `{"x": 10, "y": 20}` 的字典。它做的是：

1. 为这个对象创建一个 **Map（隐藏类）**，记录：有两个属性 `x` 和 `y`，分别在偏移 0 和偏移 1 的位置
2. 对象体内只存两个值：`10` 和 `20`
3. 下次访问 `point.x` 时，V8 通过 Map 知道 `x` 在偏移 0，直接按偏移读内存，和 C 语言结构体字段访问一样快

## 3. 隐藏类（Hidden Class / Map）

### 3.1 形状跟踪

每次给对象添加新属性，V8 就生成一个新的 Map，并记录转换关系：

```js
const obj = {};        // 初始 Map C0（空对象）
obj.a = 1;             // C0 → C1（添加属性 a）
obj.b = 2;             // C1 → C2（添加属性 b）
```

V8 内部维护一棵 **转换树（Transition Tree）**：

```
        C0 (空)
         │ add 'a'
         ▼
        C1 {a}
         │ add 'b'
         ▼
        C2 {a, b}
```

这样一来，所有按相同顺序创建相同属性的对象，会共享同一个 Map：

```js
const o1 = {}; o1.a = 1; o1.b = 2;  // Map C2
const o2 = {}; o2.a = 3; o2.b = 4;  // 也是 Map C2（共享）
```

### 3.2 描述符数组（Descriptor Array）

Map 里还挂着一个描述符数组，记录每个属性的元信息：

| 属性名 | 槽位偏移 | 属性类型 | 属性特性 |
|--------|---------|---------|---------|
| `a` | offset 0 | Double | writable, enumerable |
| `b` | offset 1 | Tagged | writable, enumerable |

**对象本体只存值，不存 key**。key 和元数据都在 Map 的描述符数组里，被同形状的对象共享——这就是省内存的关键。

### 3.3 内联缓存（Inline Cache, IC）

Map 机制配合内联缓存，让属性访问极快：

1. 第一次执行 `point.x`，V8 不知道 `point` 的形状，走通用逻辑（慢）
2. V8 在字节码调用点记录："上次遇到的对象 Map 是 M1，`x` 在偏移 0"
3. 下次再执行 `point.x`，V8 先检查对象的 Map 是不是 M1：
   - 是 → 直接按偏移 0 读（快，一次内存比较 + 一次加载）
   - 不是 → 去慢路径

这就是为什么 V8 里"同形状对象"比"异形状对象"快很多——形状一致 = Map 命中 = IC 命中。

## 4. 属性存储的分层

V8 把属性存储分了几个等级，按性能从高到低：

| 层级 | 存储位置 | 速度 | 说明 |
|------|---------|------|------|
| **Fast Property（in-object）** | 对象体内的固定槽位 | 最快 | 按偏移直接访问，类似 C struct 字段 |
| **Property Backing Store** | 单独的 FixedArray | 快 | 属性多了之后溢出到外部数组 |
| **Dictionary Mode（慢属性）** | 哈希表 | 慢 | 属性顺序不固定、或删除属性后降级 |

**性能建议**：

- 构造函数里一次性初始化所有属性，不要中途动态加属性——避免 Map 频繁转换
- 不要随意 `delete` 属性——会让对象从 fast mode 降级到 dictionary mode
- 多个对象按相同顺序初始化属性——共享 Map，IC 命中率高

## 5. 数组（Elements）的表示

数组对象的 `Elements` 指针指向一块单独的后备存储：

```
JSArray 对象
├── Map 指针
├── Properties（通常为空）
├── Elements ──→ FixedArray [ elem0, elem1, elem2, ... ]
└── length（在 Map 或对象体内）
```

V8 还根据元素类型把数组分成不同 **Elements Kind**：

- **PACKED_SMI_ELEMENTS**：紧凑、全是小整数（最快）
- **PACKED_DOUBLE_ELEMENTS**：紧凑、全是 double
- **PACKED_ELEMENTS**：紧凑、任意类型
- **HOLEY_***：有洞（稀疏数组，中间有空槽）

从 PACKED_SMI 升级到 PACKED_ELEMENTS 是快路径，但一旦变成 HOLEY（稀疏），性能就下降。

## 6. 函数与代码的内存布局

函数在 V8 里也是对象，但它的内部结构更复杂，因为函数既要能被调用，还要关联它的代码、闭包环境和优化状态。

### 6.1 函数对象的核心组件

```
JSFunction（函数对象本身，可被调用）
├── Map 指针
├── SharedFunctionInfo ──→ 函数的"静态"信息（源码、参数个数、字节码）
├── Context ────────────→ 词法环境（闭包捕获的变量）
├── FeedbackVector ─────→ 运行时收集的类型反馈（供 JIT 优化用）
└── Prototype 等
```

四个关键对象各司其职：

| 对象 | 作用 | 是否共享 |
|------|------|---------|
| **SharedFunctionInfo** | 函数的静态元信息：源码位置、参数个数、字节码、是否 strict | 同一份源码共享一份 |
| **JSFunction** | 函数的可调用对象，每次调用/每次闭包创建一份 | 每次创建闭包一份 |
| **Context** | 词法环境，保存闭包捕获的自由变量 | 每个闭包一份 |
| **FeedbackVector** | 类型反馈：这个函数被调用时见过什么类型 | 每个 JSFunction 一份 |

### 6.2 为什么要拆成这么多对象

```js
function makeAdder(x) {
  return function(y) { return x + y; };
}

const add5 = makeAdder(5);
const add10 = makeAdder(10);
```

`add5` 和 `add10` 是两个不同的 JSFunction，但它们：

- **共享同一个 SharedFunctionInfo**（同一份源码、同一份字节码）
- **各自有自己的 Context**（分别保存 `x=5` 和 `x=10`）
- **各自有自己的 FeedbackVector**（独立收集类型反馈）

这种拆分让"代码"和"运行时状态"分离：代码字节码只存一份，省内存；每个闭包的环境独立，正确性有保证。

### 6.3 代码是怎么存的

V8 的编译管线是分层的：

```
源码 (JS)
   │
   ▼  Parser + 字节码生成
SharedFunctionInfo 里的 Ignition 字节码
   │
   ▼  解释执行，同时收集 FeedbackVector
   │
   ▼  热点函数触发优化编译器（TurboFan / Maglev）
优化后的机器码（Code 对象）
   │
   ▼  如果运行时类型变了 → 反优化（Deoptimization）
退回解释执行
```

内存布局上：

- **Ignition 字节码**：存在 SharedFunctionInfo 关联的 `BytecodeArray` 里，是中间表示
- **优化后的 Code**：TurboFan 生成的原生机器码，存在单独的 Code 对象里，JSFunction 通过 FeedbackVector 关联
- **FeedbackVector**：记录每个调用点见过的类型（"这里参数总是 SMI"），是 JIT 优化的依据

## 7. 实际性能启示

理解了内存布局，可以推出这些写代码的最佳实践：

1. **对象初始化要一致**：同类型对象按相同顺序建属性，共享 Map，IC 命中率高
2. **避免动态增删属性**：频繁加属性 = Map 频繁转换；delete = 降级到字典模式
3. **数组保持紧凑**：不要制造稀疏数组，元素类型尽量统一
4. **热点函数稳定**：JIT 基于类型反馈优化，如果参数类型忽变，会反复反优化
5. **闭包的代价**：每个闭包一份 Context + FeedbackVector，不是零成本
